# reinforcement-learning-and-mcts-sample-code（Kiyota公式、655票）

## 3行サマリ
- 公式サンプル。`search_begin`/`search_step`によるAlphaZero風の決定化MCTS（隠れ情報は乱数でサンプリングして1つの完全情報局面に固定してから探索）と、盤面全体をsparse EmbeddingBagで符号化するTransformer価値・方策ネットワークを組み合わせ、自己対戦で学習データを生成する一連のパイプラインを提示している。
- ノード評価は末端までのロールアウトではなく毎回NNで即時評価（value, policyヘッド）し、UCB風の式`c*prob/(1+visit)`（c=0.4*sqrt(parent.visit)）で子を選ぶ。SEARCH_COUNT=10と極めて浅い探索で、方策損失ラベルは「未訪問の子は最悪訪問済みの子より僅かに悪い」という代入(`min_value - v - 0.03`)で埋める。
- 学習ラベルはゲーム終了後に逆順で TD(λ)風（LAMBDA=0.9）に合成（`value = value*LAMBDA + sample.value*(1-LAMBDA)`, `label=(value+sample.value)*0.5`）。時間管理・タイムアウト対策のコードは一切ない（教育目的のミニマル実装）。

## 盗めるアイデア
- ★ `search_begin`での隠れ情報の決定化パターン: `your_deck=random.sample(...)`で自分の山札の並びだけ乱数決定、相手の山札は`[1072]*deckCount`（カビゴン固定）、相手手札は`[1]*handCount`（基本エネルギー固定）、相手アクティブ不明時も`[1072]`で埋める、という「不明情報を単純なプレースホルダーで埋めてから1つの完全情報局面として探索する」実装が具体的に示されている。自作の探索エージェントを作る際の雛形になる。
- ★ 複数選択（`obs.select.maxCount`が2以上）のオプション列挙を、`indices`配列を使った「nCkの組み合わせ列挙」で表現し、64通りに打ち切ってから各comboを1つの"行動"としてNNに与えている。maxCount>1の局面（同時に複数カードを選ぶ等）をMCTSの行動空間としてどう表現するかの具体例。
- ★ 探索木のvalueは常に`your_index`（探索を開始した固定プレイヤー）視点で符号反転して管理している(`if current.state.observation.current.yourIndex != your_index: v = -v`)。相手手番のノードでも同じ木を共有する探索実装で相手視点/自視点の符号を一貫させるための典型的な実装パターン。
- ★ 訪問数最大の子を最終手として選択（PUCT探索でよくあるrobust child選択）、かつルート直下の各子ノードの`total/visit - root平均`を方策学習ラベルとして再利用する（探索結果を教師信号に変換する具体的な式）。
- EmbeddingBag(mode="sum")による疎な特徴符号化（盤面の各ポケモンのエネルギー0.5倍、ツール1.0倍、手札0.25倍、山札0.25倍などの重み付き集計）は、可変長の集合特徴量をpaddingなしで埋め込む軽量な手法として参考になる。

## 注意点・疑問
- 探索は`SEARCH_COUNT=10`と極めて浅く、壁時計での時間予算やタイムアウト時のフォールバックが一切実装されていない。CLAUDE.mdが要求する「探索系エージェントは時間制限を確認し保守的な予算+フォールバックを実装」という方針に反する形で、このサンプルをそのまま真似ると本番でタイムアウトするリスクがある（要検証：1手あたりの許容時間が不明な現状では、NN評価コストと探索回数の見積もりが必須）。
- `opponent_hand`を常に「全て基本エネルギー」（card id 1）とみなして決定化しており、実際の相手の手札分布（トレーナーズや進化カードを持っている可能性）を無視している。これが探索の質にどの程度悪影響するかは未検証。
- ノートブックで示されている学習ループはごく短い（5イテレーション×自己対戦100戦、SEARCH_COUNT=10）デモであり、性能や勝率の主張は一切していない（あくまでAPI利用例としての位置づけ）。
