# multiply-agent-best-940-lb（Ivan Ternovskiy、LB940、44票）

## 3行サマリ
- 前述の運営サンプル「Mega Lucario ex」系ヒューリスティック（Makuhita/Hariyama＋Riolu/Mega Lucario ex＋Lunatone/Solrock、Crustle対策・水デッキ対策込み）を`AdvancedPolicy`クラスとしてオブジェクト指向に整理し、その上に**ビームサーチ（BEAM_WIDTH=3）**を`search_begin`/`search_step`で実際に有効化（`USE_SEARCH = True`、`SEARCH_TIME_BUDGET = 1.5`秒）した意欲的な実装。
- `SEARCH_ALGO`は、ヒューリスティックが上位に評価した最大6候補の初手それぞれについて`search_step`で1手進め、以降は幅3のビームで最大4段階（相手ターンに移る/ターン終了までの間）まで展開し、`evaluate_state`（サイド差×10000＋盤面のエネルギー数・HP等）で評価して最良の初手を選ぶという、探索APIをフル活用した設計。
- ノートブック名の「LB940」という実績はあるが、ノートブック内には自己対戦での検証コードが一切なく（デッキ定義とmain.py本体、submission.tar.gz作成のみ）、探索を含むこのバージョンの勝率が実測されているかは不明。

## 盗めるアイデア
- ★ 実際にビームサーチを`search_begin`/`search_step`で回し、かつLB940という実運用実績がある点はこのグループ中で唯一。**「探索系エージェントが実際にKaggle環境で動いた」という事実そのものが貴重な情報**——CLAUDE.mdにある「Kaggle環境の1手あたり時間制限は未確認」という懸念に対し、少なくとも`SEARCH_TIME_BUDGET=1.5秒`・`BEAM_WIDTH=3`・候補数6・展開4段のビームサーチでLBに乗った実例として参考になる（ただしこの制限内で本当に安定して動作したかはノートブック内では検証されていない）。
- 探索ループ内で相手ターンに入った・ゲーム終了した時点で展開を打ち切る終了条件（`cur_obs.current.yourIndex != obs.current.yourIndex`、`result != -1`）や、MAIN以外のコンテキスト（サブ選択）はヒューリスティックでgreedyに解決してからMAIN選択のみ分岐する、という「探索は自分のメインフェーズの意思決定にのみ使い、強制サブ選択はheuristicに委譲する」という実装方針は、探索コストを抑える上で参考になる。
- `AdvancedPolicy`というクラスにまとめてobs解析・カウント集計・スコアリングを1オブジェクトに閉じ込める設計は、strong-start-baseline版の関数ベース実装より整理されており、探索中に何度もインスタンス化して呼び出す用途（1手ごとに新しい局面でスコアリングし直す）に向いている。
- Crustle検出時の細かい追加チューニング（例：Crustle戦ではHariyama/Makuhitaへのエネルギー付与優先度を上げる、Hariyamaのベンチ→アクティブ選択スコアを上げる等）が前バージョンより丁寧に調整されている。

## 注意点・疑問
- 探索が実際に有効（`USE_SEARCH=True`固定、フォールバックはあるが無効化オプションが無い）な状態でLB940という実績を主張しているが、ノートブック内に自己対戦や時間計測の検証コードが一切ない。1.5秒の予算がKaggle実行環境の実際の時間制限内に収まっていたかどうかは不明であり、要検証（本プロジェクトのCLAUDE.mdが警告している「時間制限未確認のまま探索系を提出するリスク」がまさに当てはまる）。
- `MCTS_ITERATIONS = 15`という定数が定義されているが、実装内のどこからも参照されていない（未使用変数、または実装が途中で切り替わった痕跡の可能性）。名称に反してMCTSではなく単純なビームサーチのみが実装されている。
- `rollout_turn`関数が定義されているが`agent`関数からも`SEARCH_ALGO`からも呼び出されておらず、デッドコードの可能性がある。
- 探索の`search_step`呼び出し回数が思ったより多くなりうる構造（初手候補最大6×ビーム幅3×最大4段）で、1手あたりの実行コストが軽く見積もっても数十回のsearch_step呼び出しになりうる点は、時間制限との兼ね合いで検証が必要。
