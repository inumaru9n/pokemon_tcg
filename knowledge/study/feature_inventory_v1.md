# 特徴量の網羅的整理 v1（ゼロベース、2026-07-13）

観測スキーマ（cg/api.py: Observation/State/PlayerState/Pokemon/Log）から、利用可能な
情報を**ゾーン別に全数調査**したもの。I-109（自己対戦RL）の特徴設計の原本。

## 原則

1. **完全観測ゾーンはカード単位、不完全観測は統計量+推論**（ユーザ設計方針 2026-07-13）
2. **自分側=カードID直接**（自デッキ60枚固定→外挿なし。ID別カウントで正確）
3. **相手側=カード属性ベースを基本**（HP/タイプ/ステージ/プライズ価値/攻撃テーブル由来の
   打点。メタの未知カードにも外挿可能）**+トップメタ約30種のID one-hot**（特異的な対面知識用）
4. 「スナップショットで取れる」vs「**履歴追跡が必要**（logsの累積、エージェント側で状態保持）」を区別

## C. 対戦文脈（共有）

- turn、firstPlayer（**先後**。現行特徴に無し）、stadium（id+所有者）、
- プライズレース: 自残−相手残、両者の「あと何キルで勝ち/負け」（プライズ価値考慮）

## D. 導出層（raw→計算述語。ゾーンの上に載る）

EXP-056で実証済みの型（1-ply計算が探索の1階近似になる）:
- 被脅威: 次ターン相手の最大打点×対象別、確定KO有無、取られるプライズ数（B2/B3+弱点）
- 与圧力: 次ターンの自分の最大打点（PH=手札数依存）、確定KO可否、リーサル距離
- 資源: エネルギー勘定（手札+山残−必要数）、進化ライン成立性（手札×場×プール）、山切れ距離（両者）
- レース: 上記を組み合わせた「先に取り切るのはどちらか」の枚数勘定

## E. 履歴層（logs累積。エージェント側で状態保持が必要）

- B1の相手手札追跡（serial単位）
- 相手の能力使用履歴（Fez/Dudの使用頻度→ドロー消費ペース）
- 攻撃履歴（相手の選好: どの標的を狙うか）※模倣でなくRLでは優先度低

## 次元の総計目安

自分側 ~120 + 相手側 ~65 + 文脈/導出 ~30 = **~215次元**（履歴層除く）。
GBT/MLPには十分小さく、自己対戦の数十万サンプルに対して過学習圏外。

## 現行実装（EXP-054〜056の99特徴）との差分 = 新規に取れる情報

1. **相手トラッシュの資源勘定**（B4。特に残Boss数=ベンチ育成の安全度が変わる）
2. **山∪サイドのプール多重集合**（A5/A6。現行はpool0として列挙内部にあるが特徴化していない）
3. **preEvolution/tools**（A2。Candy経由・ツール有無）
4. **相手手札の既知カード追跡**（B1履歴。実装コスト中）
5. **先後（firstPlayer）**（C。1次元でタダ）
6. 相手ベンチの属性集計の体系化（B3。現行はhp/prize/veilのみ）

## 用途と注意

- 第一用途: **I-109（自己対戦RLの価値関数入力）**。模倣（一致率）はEXP-053〜056で
  天井確定のため、このインベントリを模倣の再挑戦に使わないこと
- 実装時は「学習/推論のパリティ」原則（EXP-055）を維持: 特徴計算は1つのコードパスで
  リプレイ・自己対戦・推論すべてに共用する
