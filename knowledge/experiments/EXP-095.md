## 2. 設計判断: 訓練分布にプールを混ぜない

**評価の不忠実は測定を歪めるだけだが、訓練の不忠実は方策そのものを歪める**。
RLは訓練相手にbest-responseするので、083相手に訓練すれば「Spidopsは勝てる」と学習し、
本番で5%の負け対面に自ら飛び込む方策ができる。

当初案では「本番メタを知っているのだから実プールをシェア重みで訓練に混ぜる」を
我々固有の強みとしていたが、**監査結果により撤回**。AlphaStar原設計どおり
**訓練は自己対戦＋過去自己スナップショットのみ、プールは評価専用**とする。

## 3. Stage 0: ベクトル化自己対戦生成器

### 前提の発見: エンジンは1プロセス複数バトルに対応している

`cg/sim.py` の argtypes を読むと、C APIは**全て battlePtr を引数で受け取る**
（`lib.Select(ptr,...)` / `lib.GetBattleData(ptr)` / `lib.BattleFinish(ptr)`）。
1プロセス1バトルに縛っているのは `cg/game.py` の `Battle.battle_ptr`（クラス属性）だけ。
→ **エンジン改造なしに並行化できる**（`selfplay/vecenv.py`。`cg/game.py` は提出物の
経路なので変更しない）。

**並行安全性の実証**: 同一シードで「1バトルずつ逐次」と「24バトル同時」を比較 →
**勝敗+手数が24/24一致**。エンジンにバトル跨ぎの共有状態は無い。

### 検証結果（すべて事前登録した項目）

| 項目 | 結果 |
|---|---|
| アリーナとの一致（同一engine seed、32試合） | **勝敗32/32・手数32/32が完全一致** |
| バッチ推論と逐次推論の数値一致 | 165決定で最大絶対差 **3.8e-06**、argmax 165/165 |
| スループット（6ワーカー、フル情報特徴つき） | **49,685試合/時**（計画値33,000を50%超過） |
| エンジン+JSONの下限 | **0.659 ms/決定**（従来のハーネス経由1.47msから2.2倍改善） |

### コスト内訳（1決定あたり、実測）

| 要素 | ms |
|---|---|
| エンジン + JSON | 0.659 |
| `to_observation_class` | 0.296 |
| `featurize`（自分/相手 各0.115） | 0.229 |
| NN forward（バッチ化後） | ~0.1 |

**バッチ化でNN forwardが生成コストの62%（2.4ms/決定）から約4%に落ちた**のが効いた。
残るボトルネックはエンジンのJSONシリアライズで、これ以上はエンジン改造が必要。

### 大規模生成でだけ出た失敗（3件、いずれも小規模スモークでは露呈しない）

**(a) ワーカーの戻り値をPythonオブジェクトのままにすると親が破裂する**
`_run_chunk` が系列を Python の list（126要素×2＋48＋3のfloat list）で返し、`ex.map` の結果を
`list()` で全部持つ構造だった。4万試合＝約620万行×310個のPython float（1個24バイト）で
数十GB規模になり、**親RSS 2GB・スワップ4.35GB・27分でCPU時間7秒**という空転状態に陥った。
64試合のスモークでは小さすぎて露呈しない。
→ **ワーカー内でnumpy(float16)に詰めて返し、一定行数ごとにシャードへ書き出して親を解放する**。
修正後はピーク690MBで頭打ちすることを実測で確認してから本番投入する運用に変えた。

**(b) `max_tasks_per_child` は macOS+spawn でデッドロックする**
libcgのリーク対策として `ProcessPoolExecutor(max_tasks_per_child=8)` を使ったところ、
**シャード1本目の直後にワーカーが全滅し、親とresource_trackerだけが残って空転**した
（再現性あり: 2回とも同じ挙動、`--tasks-per-child 100000` で無効化すると毎分1シャードで安定）。
→ **既定で無効化**。libcgのリーク対策は「**1プロセスあたりの試合数を2万に抑えてプロセスごと使い捨てる**」に変更。

**(c) 「遅い」を「壊れている」と誤診した**
(a)の直後、スワップ枯渇で起動が這っていた健全なジョブを、**ワーカー検出のgrepが誤っていた**
（`[m]ultiprocessing.spawn` は正常動作時もマッチせず0と表示される）ために停止させた。
→ プロセスの生死は**成果物（シャードの増加）とCPU時間**で判定する。プロセス名のgrepは使わない。

### 実装上の注意（記録）

- **強制手（選択肢1個かつminCount>0）ではLSTMを進めない**。094のmain.pyと同一規約にしないと
  学習系列と生成系列のステップ数がズレる（EXP-094 v7の穴の再発防止）
- LSTM状態は **(バトル, プレイヤー) 単位**で持つ。自己対戦でも両者は別の観測列を見る
- `GetBattleData` の `search_begin_input`（探索用バイナリblobのasciiデコード）は
  自己対戦では不要なので作らない
- **ワーカー再生成(`max_tasks_per_child`)は使わない**（上記(b)）。libcgのリーク対策は
  「1プロセスあたり2万試合でプロセスごと使い捨て」で代替する
- **平均ステップ数はエンジンのシード有無で大きく変わる**（シード無し454 / シード有り162）。
  比較する数字は必ず同一条件で取ること

## Kaggle NotebookでRLループを完結できる（実測で確認）

**コンペ紐付けだけでエンジンのC++ソースが見える**:
`/kaggle/input/competitions/pokemon-tcg-ai-battle/ptcg_engine/ptcgProgram 22`
→ データセットへのソース同梱は不要。

**CRNパッチ入り libcg.so をKaggle上でビルドできる**（実測37秒、g++ 11.4、
`nm -D | grep BattleStartSeeded` = 1）:
```
g++ -std=c++20 -O2 -shared -fPIC \
    -I "/kaggle/input/competitions/pokemon-tcg-ai-battle/ptcg_engine/ptcgProgram 22" \
    -o /kaggle/working/cg/libcg.so <データセット>/cg/Export_seeded.cpp
```
**これは必須**。配布の `libcg.so` はリポジトリの `cg/libcg.so`（07-04版）と**ハッシュが異なり**、
かつ `BattleStartSeeded` を持たない。ソースからビルドすれば **07-15版エンジン + CRN** が
Kaggle側でも揃い、ローカルと同一条件になる。

**落とし穴**: `cg/` のPythonラッパは**必ず自前のデータセット側を使う**。コンペ配布側の
`cg/sim.py` にはローカルで追加した `HAS_SEEDED_START`（CRNの能力検出）が無く、
`from cg.sim import HAS_SEEDED_START` で ImportError になる（実際に1回踏んだ）。

**設計上の含意**: RLループ（生成→advantage→PPO更新→再生成）は**1つのノートブック内で
完結できる**。重みはメモリ上で更新されるので、イテレーションごとのアップロード往復は不要。
セッションを跨ぐときだけ `/kaggle/working` にチェックポイントを置く。

**【撤回した誤り】「Kaggleは生成が9倍遅い」**: 初回測定（Kaggle 7,234試合/時 vs ローカル
63,000試合/時）は **Kaggle側だけ `max_tasks_per_child=8` が有効なまま**の非統制比較だった。
ローカルで無効化した後、**Kaggle側の測定値を取り直さずに計画を決めた**のが誤り。
統制した再測定では **Kaggleのほうがエンジン+JSONで1.6倍速い**（0.405 vs 0.659 ms/決定）。
→ **基盤の設定を変えたら、その設定で取った過去の測定は全て無効として測り直す**。

**アクセラレータは必ずID名で指定する**（`--accelerator NvidiaTeslaT4`）。
`enable_gpu: true` だけだと**P100が割り当てられ**、sm_60はKaggleイメージのPyTorch(sm_70+)と
非互換でCPUフォールバックする。EXP-094で記録済みの教訓を今回踏み直した
（12時間セッションを空費しかけた。ユーザ指摘で発覚）。

### 生成コストの工程別内訳（Kaggle T4、torch backend、batch=256）

**PPOではオンポリシー生成が毎イテレーション走るので、この内訳が全体のコストを決める。**

| 工程 | ms/決定 | 割合 |
|---|---|---|
| **engine（Select + JSON）** | **0.347** | **36.2%** |
| obs変換（`to_observation_class`） | 0.223 | 23.3% |
| featurize（自分＋相手の2回） | 0.188 | 19.6% |
| NN前向き | 0.159 | 16.6% |
| 選択肢構築（option_vector/class） | 0.040 | 4.2% |
| 合計 | **0.956** | |

| backend | batch | ms/決定 | 決定/秒 |
|---|---|---|---|
| numpy | 32 / 128 / 256 | 1.390 / 1.396 / 1.191 | 695 / 701 / 822 |
| **torch(GPU)** | 32 / 128 / **256** | 0.939 / 1.092 / **0.956** | 974 / 896 / **1024** |

**GPU化の効果は1.25倍（1.191→0.956 ms）にとどまる**。NN単体は 0.138→0.159 ms とむしろ微増で、
改善の実体はnumpyのスレッド競合が減った副次効果。**バッチを32→256に上げても伸びない**
＝1.2Mパラメータの小さいLSTMではGPUの利点が出る規模に達していない。

**教訓: 「NNが支配的」という直感は外れる。** 当初「NN 0.9ms（全体の42%）」と見積もったが
実測は0.16ms（17%）。FLOPs換算での再見積もり（0.25ms）のほうが正しかった。
**最大の費目はエンジンのJSON往復（36%）で、次がPython側のobs変換+featurize（43%）**。
最適化するならこの順。

## 設計判断: 価値関数は方策とネットワークを共有しない

**AlphaStarの実際の設計**は「LSTMコアを共有し、価値ヘッドの直前で相手の観測エンコードを
連結する（特権ブランチ）」であって完全な別ネットワークではない。それでも本計画は
**別ネットワークから始める**:

1. **特権情報の漏洩経路を物理的に断つ**。共有トランクに相手の手札を入れれば方策が使えてしまう。
   AlphaStarは配線で防いでいるが、別ネットワークなら配線ミス自体が起こらない
   （EXP-094で次元/キー並び/未学習ctxの無言劣化を3回踏んだ経験からの判断）
2. **KLアンカーと価値勾配が競合する**。094の重みから出発してSL方策へのKLを掛け続けるので、
   共有トランクだと価値損失がトランクをSL解から引き離し、KL項が押し戻す綱引きになる
3. **共有の利点が効かない**。**Vは学習時にしか使わない**（advantage計算のみ。提出物にも生成時にも
   不要）ので共有してもコストは浮かず、リスクだけ残る。加えて方策は強制手でLSTMを進めない規約
   なので、共有するとVの評価点が方策のステップ schedule に縛られる

**キルゲートを単独GBTで測るのも意図的**: 問いは「信号があるか」であって「どのアーキテクチャか」
ではない。副産物として、**GBTは再帰も履歴も持たないので、これでAUCが立てば「完全情報の盤面は
ほぼマルコフでフィードフォワードのVで足りる」ことの証拠になる**。GBTで立たずLSTM版で立つなら
「Vには履歴が要る」という別の知見。

AlphaStar式の共有コア＋特権ブランチは、別ネットワークのVがunder-fitする兆候が出てから試す。

**ターン5以降の平均AUC 0.8574**（事前登録の閾値0.75を大きく超過）。全体AUC 0.8169。

### 初回が「保留」と出た本当の理由は**valの精度不足**だった（自己訂正）

初回（val 2,381試合）は単調性チェックが最終帯 t15-99 の落ち込み（0.916→0.884）で不合格になり、
私は「catch-all帯を単調性に含めたのが基準設計の誤り」と結論した。**これは誤診**。
後の曲線測定で**valを5,066試合に増やすと、20k以上で単調性も満たしてPASS**になった。

→ **基準そのものを疑う前に、測定精度が足りているかを疑うべきだった**。判断の順序が逆。
val規模が小さいと末尾帯（サンプルが最も少ない）のノイズが真っ先に効く。

### 暖機（094からの重みコピー）の効果は**ゼロ**

| | 全体AUC | t5以降平均 |
|---|---|---|
| スクラッチ | 0.8169 | 0.8574 |
| 094暖機 | 0.8167 | 0.8572 |

差は無い。**SL表現は価値推定に転移しない**＝価値関数は自己対戦データから独自に表現を学べる。
暖機の実装は正しく動いていた（初期時点でトランク出力が方策と**厳密一致**、相手盤面を
10倍の乱数に振っても出力不変＝特権ブロックが0、を検証済み）ので実装ミスではない。
→ **Stage 2 以降も価値関数はスクラッチ初期化でよい**（暖機の配線を保守する必要がない）。

### 留保: このAUCは「EXP-055の交絡が解けた」証明にはならない

EXP-055の観察データ由来の勝率回帰も**全体AUC 0.79**を出していた。あちらの問題はAUCの
低さではなく「勝者の盤面と相関するものを選ぶが、勝ちに向かう行動を選ばない」という
**行動選択への使えなさ**だった。したがって高AUCだけでは交絡解消の証拠にならない。

ただし**PPOでの用途には十分**: Vはbaselineとして分散削減に使うだけで、**偏っていても
方策勾配は不偏のまま**（バイアスは分散にしか影響しない）。因果的な正しさが要求されるのは
後段の価値誘導探索のほうで、そちらに進むときに改めて検証が必要。


## Stage 1 の締め: データ量スケーリング曲線

**目的はVの改善ではなく「PPOの各イテレーションに何試合必要か」を決めること**。

|---|---|---|---|---|

### 測定設計の落とし穴（実行前に潰した）

当初の実装は `--limit-games` で**先にデータを絞ってから分割**していたため、
データ量ごとに**val集合が別物**になっていた。判定したいのは「1倍化あたり0.01の改善」だが、
val規模1,200〜4,800試合では**val集合の違いだけで0.005〜0.01の揺れ**が出る＝効果と同じ大きさの
ノイズが混ざり、測定として成立しない。**valを全データから先に固定し、limit-gamesは学習側だけ
を絞る**よう修正（3点でval集合のハッシュ一致を検証してから投入）。

**教訓: 比較実験は「変えたい要因以外が動いていないか」を実行前に検証する**。
EXP-094 v9（学習シード）、Kaggleの「9倍遅い」誤測定に続き3件目。

## Stage 2a: 探索温度の決定

PPOには探索が要るのでargmaxからサンプリングに変える。その代償を実測した
（サンプリング方策 vs argmax方策、同一重み、**先後を交互に入替**、n≈1,020）:

| 温度 | 強さのコスト | 平均エントロピー | argmax一致率 | argmaxと違う手/試合 |
|---|---|---|---|---|
| 0.3 | ほぼ0（51.4%） | 0.119 | 95.3% | 約3.8 |
| 0.5 | −3.6pt（46.4%） | 0.184 | 92.2% | 約6 |
| **0.7（採用）** | **−3.7pt（46.3%）** | **0.289** | **89.0%** | **約9** |
| 1.0 | −8.9pt（41.1%） | 0.406 | 84.3% | 約13 |

**T=0.5はT=0.7に支配される**（コスト同じで探索量1.6倍）。T=1.0はコスト2.4倍で割に合わない。
このコストは**データ生成側の方策**にかかるもので、提出する最終方策（argmax評価）の強さではない。

**初回測定はサンプリング側をseat0に固定していて先手有利（50-53%）が混入し、
「T≤0.7はコストゼロ」という誤った結論を出した**。先後入替で常識的な形になった。

### 懸念: 方策が尖っており、KLアンカーと低エントロピーが両方「変わるな」に働く

選択肢が平均8個（最大エントロピー ln8=2.08）なのにT=1.0でもエントロピーは0.406。
教師を82%忠実度で模倣した結果、確信度の高い方策になっている。
AlphaStarはエントロピーボーナスを使わずKL正則化だけで運用するが、あちらは巨大な探索量で
押し切れる側。**我々の規模ではKL係数を強くしすぎるとPPOがほとんど動かない可能性**がある。
→ Stage 2b で**KL係数を振って「方策が動くが壊れない」帯を探す**ことを最初の項目にする。
