### ★ 監査で見つかった2件

**(a) デプロイした重みが val loss の最小点を過ぎている**

```
ep019  val loss 0.4811 ← 最小        val acc 0.8606
ep031  val loss 0.5045 (+4.9%)      val acc 0.8638 ← **104はこれ**
ep039  val loss 0.5228              val acc 0.8631
```

`--stop-metric` の既定が `acc` のため。acc は +0.32pt しか上がらないのに loss は 4.9% 悪化
＝**確率が過信方向に壊れている**。argmax で打つ限り影響は小さいが、
**ExIt の候補生成は `top1 − top2` のギャップで局面を選ぶ**ので、そこには効く可能性がある。

**(b) value head スイープ（EXP-101 v1）の成果物が全て104と同一だった**

`out_vhead104/` の4条件（vh0/vh64/vh64_s2/vh128）は、
**保存された方策の重みがビット単位で104と一致**し MAIN一致率も全て 0.8333。
ログは val=0.7825/0.8070/0.8039/0.8067 と別々の値を出しているので、
**評価した重みと保存した重みが別物**。EXP-101 の「重み設定ミスで判定不能」と整合する。
→ **補助ヘッドは本当に未検証**（やるなら保存側の修正が先）。

## 2. アンサンブル（3本の確率平均）

### なぜこれを選んだか

軸A/B/Cが全滅した理由は「改善が小さくノイズ床（学習シードのsd 1.81pt）に埋もれる」。
アンサンブルは**改善を賭ける操作ではなく、そのばらつき自体を縮める操作**なので性質が違う。
さらに再学習が不要（`data/nn/out_feat104/` に3シードの重みが保存済み）。

### 実装

`tools/featgen_nn.py` に `EnsemblePolicy`。要点は3つ。

```
1. **各メンバーが独自のLSTM状態を持つ**。層の意味が個体ごとに違うので状態は混ぜない。
   実際に選ばれた手（prev）だけが全メンバーに共通で流れる
   ＝「1本の行動軌跡を共有する方策のアンサンブル」
2. **合成は決定ごとの softmax を平均してから log**。生スコアの平均は誤り
   （ctx_bias/ctx_scale が個体ごとに学習されるのでスケールが違い、
     確信の強い個体でなく**スケールの大きい個体**が勝つ）
3. 起動時に feat_keys / classes / vocab / 入力次元 / head をメンバー間で突合
```

104 = **d20_s2**（3本の val 最良）とビット一致を確認済み。よってアンサンブルは
「best-of-3 に対して勝てるか」を問うている。

## ★ 結論と、その意味

**val +0.86pt が、プールでは ±0.00pt。** これは EXP-100 の再確認以上の情報を持つ。

### (a) 残差誤差は分散ではなくバイアス

アンサンブルは**推定の分散成分だけ**を消す操作である。それで何も得られなかったということは、
**3本のシードは同じ間違いをしている**＝104の残る誤りは「学習のばらつき」ではなく
**教師データと特徴表現が決めているバイアス**。

これは「模倣の磨き込み」路線全体への否定的証拠になる。同じデータ・同じ特徴で
初期値を変えるだけの操作は、もう何も生まない。**変えるならデータかラベル**
（＝ExIt / 教師の追加）しかない。

### (b) 効いた枠は「教師に存在しない相手」だった

伸びた2枠 Ogerpon(+3.25) と Dragapult(+3.00) は、どちらも**訓練データ（Yushin 07-17〜29）に
存在しない相手**。EXP-113 で軸Aが「Ogerpon も Lopunny も学習していない」と指摘したのと同じ構図。

**アンサンブルの利得は分布外でのみ現れ、分布内（Marnie w48.3）ではむしろ微減する。**
そして本番メタは Marnie が半分を占めるので、加重では相殺される。

### (c) 測定装置としては成功

CRNペア（同一 engine-seed・同一 n=1200）により、9対面すべてで差が ±3.3pt 以内に収まり、
weighted で −0.03pt という**極めて安定した「差なし」**が得られた。
`--engine-seed` を通した運用（EXP-106）が効いている。

## 判断

**155 は提出候補にしない。** 加重で差が無く、推論コストが1.5倍、tar.gz が3倍になる。
分布外に強い性質は将来メタが動いたときの保険になるが、いま払う理由がない。

## 付随して修正したもの

**ExIt生成（EXP-115 Phase 1a）が3.5時間ぶんを全損して落ちていた**。

```
ValueError: Active card must be the ID of a Pokémon card.
```

- **原因1**: 相手アクティブが伏せの局面で `search_begin` が呼べない。SETUP系ctx(1/2/41)の
  除外では取り切れない局面が実在し、フォールバックで渡していた
  `sorted(FT.DECK_COUNTS)[0]`（=カードID 5）が**ポケモンではなかった**
- **原因2**: 走っていたのは `ex.map` 版で、**チャンク単位の try/except を入れる前**の
  コードだった（ファイルは更新済みでも起動済みプロセスには反映されない）。
  ログに「残り約N分」が出ていないのが旧コードの証拠

**修正**: (1) 相手アクティブが伏せの局面は**スナップショット時点で捨てる**
（偽のアクティブを捏造するとロールアウトが実局面と別物になる）、
(2) 局面ごとに try/except + `search_end()` で1局面の失敗がチャンクを巻き添えにしないようにした。

**教訓: 長時間ジョブは「起動時のコード」で走る。** 実行中のプロセスの健全性は
ログの**書式**（新しい版で追加した文言が出ているか）で確認できる。
