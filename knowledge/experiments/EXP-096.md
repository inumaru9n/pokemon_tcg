# EXP-096: デッキ汎用の特徴器ジェネレータ（プールSLレプリカの量産基盤）

- 日付: 2026-07-30
- BACKLOG: I-109（Phase RL / Stage 3 リーグの前提整備）
- 対象: `tools/gen_featurizer.py` + `tools/featgen_core.py` + `tools/featgen_main.tmpl`
- 状態: 判定保留（学習前診断はPASS。val一致率の比較はKaggle実行中）

## 背景

[EXP-095](EXP-095.md) のプール忠実度監査で、プールv4の**全枠が±5ptの忠実度ゲートを外している**
（w×乖離の合計14.7）ことが判明した。とくに Marnie 1ec0（7.40）と Spidops d5834（3.97）が重い。
レプリカ製法としてNNの優位は直接証拠がある（同一デッキで084=ルール 33.0% vs 094=NN 67.2%、vs082）。

しかし枠ごとに特徴器を手作りすると、1枠あたりEXP-094相当の作り込み（v1→v6の反復）が要る。
**5枠以上を作る前提では、この作り込みが律速**になる。

## 仮説

手作り実例2つ（094=Alakazam / 092=Marnie）を突き合わせると、**デッキ依存部分は「定数」と
「行動クラスの名前集合」だけ**で、しかも手作り述語は同じ型の機械展開である:

| 094 | 092 | 一般形 |
|---|---|---|
| `ready_zam`（Alakazam×エネ≥1） | `ready_grim`（Grimmsnarl×エネ≥2） | 種族 × エネ枚数 |
| `loaded_pre`（進化前×エネ≥1） | `charged_pre`（進化前×エネ≥2） | 進化段階 × エネ枚数 |
| `dudun3`（Dudunsparce×エネ≥3） | `munki_online`（Munkidori×エネ≥1） | 同上 |
| — | `grimline_field` / `snow_field` | 進化ライン単位の場の数 |
| `act_e_basic/telepath/enrich` | `act_e` | エネ種別カウント |

したがって deck.csv からこれらを機械展開すれば、**手作りと同等の特徴器を自動生成できる**。
固定閾値を焼き込むのでなく**枚数そのもの（合計 `e_*` と最大 `emax_*`）を出す**ことで、閾値は
MLP側が学べるため情報量は手作り以上になる。

## 方法

**構成**: 生成物 = 「deck.csvから導出した定数ヘッダ」＋「デッキ非依存の汎用コア」の連結1ファイル。

- `tools/featgen_core.py` — セクション1/2/3/5/6/7/8/9とオプション側特徴は `feat_094.py` からの
  **忠実移植**（A-1/A-2・playerIndex・toolIndex/energyIndex・NULLオプションの修正込み）。
  忠実度の保証をこの1本に集約する
- `tools/gen_featurizer.py` — `SPECIES` / `SPECIES_NAME` / `LINE_OF`（evolvesFromを辿った進化ライン）
  / `PRE_EVO` / `ENERGY_NAME` / `STADIUM_NAME` / `ATTACH_BUCKET`（ライン×最終進化か）/
  `CLS_PLAY` / `CLS_EVO` / `CLS_AB` / `CLS_ATK`（`card.attacks` = attackId列から）/ `CLASSES` を生成
- `--agent-dir` でエージェント一式（`feat_*.py` / `nn_*.py` / `main.py` / `attack_table_056.py`）を
  書き出す。**deck.csv だけからレプリカの骨組みが完成する**

**検証設計**: 手作りの正解が2つあるので、同じデッキに生成版を当てて突き合わせる。

1. **識別不能率**（学習前・安価）= 教師が選んだ選択肢と特徴が完全一致する別の選択肢が
   同じ決定内に存在する率（`tools/feat_diag.py`）。EXP-094でv5の穴A-1/A-2を発見した診断
2. **教師MAIN行動のクラス分布**（学習前）= クラス設計が手作りと対応しているかを直接見る
3. **val一致率**（学習後）= 同一スクリプト・同一3シードスイープで手作り版の実測値と比較

教師は既承認の2組と同一（新規なし）:
- Yushin Ito / sig 156952a871 / 07-17〜07-25（3,593試合・301,835決定）
- Dries @ Tufa Labs / sig 1ec0f47981 / 07-26〜07-28（833試合・76,572決定）

## 結果2: 副産物 —— 提出済み094のクラスラベルに欠陥（記録）

094の `option_class` はABILITY選択肢を `me.active if area==ACTIVE else me.bench` で解決している。
ところが**スタジアムの効果発動もABILITY型で来る**（`area=STADIUM`）。094の教師データでは
**MAIN決定の1.5%（2,811件）が相手の Spikemuth Gym の発動**で、これが `me.bench[o.index]` として
解決され、「ベンチ0番目のポケモンの特性」という**盤面状態依存のノイズラベル**になっていた。

学習と推論で同一コードなので train/serving skew ではないが、クラス頭の意味が薄まる。
092は正しく3分岐していた（`ab_gym` 10.0%）ので、092→094の移植時に落ちた退行と見られる。
生成版は正しく解決し、自デッキに無いスタジアムは専用クラス `ab_stadium` に寄せる。

**影響の見積り**: クラス頭は pointer スコアへの加算バイアスなので、誤ラベルの被害は
「1.5%の決定で加算が無意味」に留まる。094の再学習・再提出を単独で正当化するほどではないが、
プールレプリカは最初から正しい版で作る。

## 結果3: 実装の穴（いずれも効果測定と無関係に直すべきもの）

| 穴 | 影響 | 修正 |
|---|---|---|
| クラス総数を「観測max+1」で推定 | 末尾クラスが教師データに未出現だと分類ヘッド幅が足りず**推論で範囲外index**。生成版はクラスが疎（094生成は65中9個が未出現）なので現実的に踏む | `extract`→`pack`→`train` にクラス総数を明示記録。`ppo.py` / `train_nn_kaggle.py` の gather に上限クランプ |
| ABILITY の `area=STADIUM` を分岐に入れていない | 上記（094の1.5%） | 3分岐 + `ab_stadium` |
| 攻撃を `atk` 1クラスに潰す | 打ち分けがクラス頭に載らない（092は attackId で分割済み） | `card.attacks` から機械展開 |
| 進化しないたねポケモンに `evo_*` クラス | 空クラスが混ざりID全体がずれる | `basic` 属性で除外 |
| 短縮名の衝突（トレーナー名の切り詰め、種族名×スタジアム名、エネ名×ツール名、コア固定キーとの衝突） | 別カードが同じ特徴キー/クラスに**静かに潰れる**（例外は出ない） | 生成時に検査して落とす |
| ATTACHをエネしか見ていない | **ツール装着**（Hero's Cape / Brave Bangle）が全て `other` に落ちる。Spidopsの教師データでMAIN決定の1.9%。094/092のデッキにツール装着が無かったため露呈しなかった | `TOOL_NAME` を追加し、エネと同じ「対象バケット付き」クラスに（63→77クラス） |
| 所有者接頭辞で短縮名が潰れる | Team Rocket系は全カードが `team_rocket_` に切り詰められ、`_uniq` の x 付けで意味のない名前が並ぶ（衝突はしないがデバッグ不能） | `"'s "` の後ろを種名として使う。切り詰め衝突が起きたら警告 |

**測定を無効化したバグ（自己訂正）**: 上記「所有者接頭辞を落とす」修正を入れた後、
094デッキの生成特徴器を**再生成してから学習済みモデルと組み合わせた**ところ、
トレーナー名にも接頭辞除去が効いて `use_boss_order`→`use_orders`、`use_lana_aid`→`use_aid`、
`use_xerosic_ma`→`use_machinatio` と変わった。`CLASSES` はソート済みタプルなので
**クラスIDが全体的にずれ**、学習済み分類ヘッドと対応しなくなる。
この状態で 094 vs 099 を800戦回して 68.4% という値を得たが、**無効な測定**である。

検出できなかった理由: 盤面次元（158）とクラス数（65）が偶然一致していたため、
`main.py` の既存チェック（feat_keysの並び照合）は通り、クラス側は照合していなかった。
→ **モデルにクラス名の列を保存し推論時に突合する**よう `pack_dataset.py` /
`train_nn_kaggle.py` / `featgen_main.tmpl` を修正。名前が1つでも変われば起動時に例外になる。

**教訓: 次元数・個数の一致は同一性の証明にならない**。生成物と学習時の成果物は
`diff` で全文照合するか、モデル側にメタデータを持たせて機械的に突合すること。

**運用**: これらは**新しいデッキに当てて初めて出る**種類の漏れである。枠を増やすたびに
`tools/feat_diag.py` の **other系率**を確認すること（今回は1.9%という数字がそのまま原因特定に
つながった）。手作り2例だけでは発見できなかった。

## 結果6: 一致率の改善は**対戦強度に転移しない**（094ミラー）

**094 vs 099 = 48.5%** [45.1-52.0]

点推定では099が1.5pt上だが**CIは50%を跨ぐ**。学習シードのノイズ床（sd 1.81pt、EXP-094 v9）を

含意を分ける:
- **主力（094系）を生成特徴器に置き換える根拠は無い**。判断にはミラーでなくプール評価が要る（非推移性）

## 結論

**ジェネレータは validated**（2デッキ・3つの独立な指標で手作り以上）:
- val一致率: 094で **+0.83pt / MAIN +0.85pt（3シードとも非重複＝有意）**、Marnieで +0.43/+0.78pt
- 忠実度（対戦強度）: **+5.4pt改善**（62.5% → 57.1%、正解48.0%に対して）
- 忠実移植部分は値レベルで完全一致（共通109キー×20,000決定）

094の手作り版は v1→v6 まで反復して作り込んだ提出済みの版であり、**自動生成がそれを超えた**。
手作りに勝った直接の要因として特定できているのは (a) スタジアム特性の正しい解決
（手作りは1.5%の決定を盤面依存のノイズラベルにしていた）(b) 技のattackId別クラス分割
(c) 固定閾値でなく枚数そのものを出したこと の3点。

**プールへの反映（未実施・要判断）**: 083 → 098 の差し替えで Spidops枠の負債 **3.93 → 0.07**。
**098は±5ptゲートを通った唯一の枠**なので、EXP-095の設計判断（不忠実な相手を訓練分布に
入れない）の下でも**訓練分布に入れる資格がある**。
ただしプール差し替えは**過去のweighted値との比較を切断する**ので、実施はメタ更新と
まとめて行うこと（pool.jsonのweightは07-22基準で既に古い）。

Marnie枠は 082 → 097 で負債 7.40 → 3.49 に減るが、097は模倣対象が誤っている（結果9）ため
**差し替えずLucaで作り直すのが正しい**。

**INSIGHTS昇格候補**:
1. レプリカの忠実度を決めるのは製法（ルール/NN）でなく**特徴器の質**。同一のNN模倣でも
   特徴器の差だけで5.4pt動く
2. 特徴器のデッキ依存部分は「定数＋行動クラスの名前集合」に還元でき、機械展開で手作りを
   上回れる。**固定閾値を焼くより枚数そのものを出す**方が良い（閾値はMLPが学ぶ）
3. 学習を回す前に**識別不能率＋教師MAIN行動のクラス分布**で特徴器を比較できる。

# Stage 3（リーグ）の記録

## エンジンに特権情報APIを追加（`GetHiddenData`）

**発端**: EXP-095はStage 1のCriticを「相手の手札を含む完全情報を入力とする privileged
value baseline」と記述したが、**これは誤りだった**。実装は `oppb = ft.feat_vector(state, 1-me)`
＝**手番プレイヤーの観測に我々の特徴器を当てただけ**で、エンジンの観測は視点付きなので
相手の手札は `null`。つまり**特権情報は最初から入っていなかった**。

実測（099 vs 101、相手側ブロック158次元）:

| | 有効次元 | 常にゼロ |
|---|---|---|
| ミラー | 121 | 37（`hand_*` 22 + 未出現カード15） |
| 非ミラー（vs Marnie） | 70 | 88（`hand_*` + `dis_*` + `act_{種族}` + `e/emax` …） |

ミラーでは相手のトラッシュ・場・山残量が我々のID体系で写るので機能していたが、
**非ミラーではデッキIDに依存する特徴が全滅**し、生きている70次元も多くは我々自身の
情報の重複や定数（`pool_*` は相手が我々のカードを持たないので定数になる）。

**解決**: `cg/Export_seeded.cpp` に `GetHiddenData(ptr, playerIndex)` を追加（配布ソースは無変更）。
エンジンは内部に完全な `State` を持ち、視点制限は出力時にかけているだけなので、
`PlayerJson` の `myPlayerIndex==2`（観戦者モード）の経路が既に存在していた。ただし
観戦者モードは山札60枚×2＋カード名まで吐いて重いので、**隠れ領域のcardIdだけを返す
最小APIを足した**。

**踏まなかった罠（設計時に特定して回避）**:
1. `State.h:425` の `nextLogStart()` は `logIndex.at(playerIndex) = logs.size()` と
   **カーソルを進める副作用**を持つ。特権取得で呼ぶと本来の観測が受け取るログを食い潰す
2. `ApiGetBattleData` の戻り値は `data->jsonBuilder.buf.c_str()` を指すので、
   共有すると直前の観測バッファを上書きする → 専用の `thread_local` バッファを使う

**検証**: 相手手札の取得 142/142（100%、キャッシュ方式なら39.7%）、**副作用なし**
（呼ぶ/呼ばないで試合結果・手数・各ステップのログ長と選択肢数が完全一致）、CRN決定性維持、
コスト +0.06ms/決定。

## Criticを対称な bag-of-embeddings に再設計（`ValueNetV2`）

旧設計の病巣は「**Actorの特徴器をStateの符号化器に流用した**」こと。V(s)は状態の勝率で
あって視点を持つ理由がないので、両プレイヤーを同じ関数で符号化する形にした。

    V(s) = head(LSTM(enc([E(p0), E(p1), prog, logs, ctx, prev])))
    E(p) = shared([ゾーンごとのカード埋め込みの和（手札/山∪サイド/場/トラッシュ）, 汎用属性])

**カードIDをそのまま埋め込み索引に使う**ので語彙も和集合も不要。リーグにデッキを足しても
次元が変わらず、mainを差し替えてもCriticを作り直さなくてよい。
「方策とレイアウトを揃える（暖機用）」制約は捨てた——EXP-095で暖機の効果はゼロと実測済みで、
その制約を維持する理由が既に失われていた。

**検証（事前登録: Stage 1と同じ turn5+ AUC ≥ 0.75 かつターン帯で単調増加）**:

| ターン帯 | n | AUC |
|---|---|---|
| 1-4 | 6,501 | 0.666 |
| 5-9 | 9,508 | 0.746 |
| 10-14 | 5,507 | 0.799 |
| 15-19 | 919 | 0.869 |
| 20+ | 806 | **0.965** |
| **turn5以降** | 16,740 | **0.7805** ✓ |

**PASS**。単調増加も成立。特権ブロックの充填も実測で確認（両プレイヤー59.4/59.5枚＝
60枚デッキとして正しく、手札も入っている）。**advantageは有意な情報を持っている**。

## リーグが改善しない原因の切り分け

### 切り分け1: KLアンカーは律速ではない（棄却）

学習済みCriticを使い回し、方策をSL初期から同条件で走らせて KL係数を振った
（1,000試合×10イテレーション×3条件）。

| KL係数 | KL(π‖π_SL)の推移 | 1更新の移動量 | 評価(vs SL初期, n≈400) |
|---|---|---|---|
| **0.0**（アンカー無し） | 0.012 → **0.101** | +0.011 | 49.6% → 51.1% |
| 0.01 | 0.012 → 0.098 | +0.011 | 52.5% → 54.7% |
| 0.05（本走） | 0.011 → 0.060 | +0.011 | 45.1% → 50.5% |

**アンカーを外しても方策は10イテレーションでKL 0.10までしか動かない**（0.01とほぼ同一）。
6回の評価の平均は50.6%で条件間に差なし。

**副産物の重要な観察**: `klstep`（1更新の移動量）が**全条件で +0.011 と完全に同一**。
移動量を決めているのはアンカーではなく **lr(1e-4)とクリップ**である。
＝KL係数は「効かないつまみ」だった。

### 切り分け2: 探索が構造的に不足している（実測）

方策が尖りすぎており、サンプリングしてもargmaxからほとんど離れない。

**平均8個の選択肢に対し実効1.29個**。1試合80決定のうち探索は約8.5回しか起きていない。
T=2.0まで上げても実効1.92個で、模倣学習で作った尖った方策は温度では平らにならない。

### 切り分け3: 相手分布の広さは原因ではない（棄却）—— E1

**相手を101のみに固定**して20イテレーション×1,000試合＝20,000試合。
判定指標を「vs 101 の argmax勝率」1本に絞った（混合だと改善が相手ごとに分かれて埋もれる）。

| 区間 | 訓練中の勝率(T=0.7) |
|---|---|
| it0-3 | 43.6% |
| it4-7 | 43.6% |
| it8-11 | 43.3% |
| it12-15 | 44.9% |
| it16-19 | 44.4% |
| **前半5回 → 後半5回** | **44.1% → 44.5%** |

argmax評価: 41.0 / 43.8 / 40.5 / 43.2 / 44.5%（平均 **42.6%**）。
**学習前の 099 vs 101 = 45.6%(n=399) を下回る**。

方策は動いている（KL 0.012→0.096）のに**良くならない。むしろわずかに劣化**。
＝**単一相手でも改善できない**ので、相手分布の広さは原因ではない。

### 残る仮説（検証中）

| 仮説 | 状態 |
|---|---|
| ① 相手分布が広すぎて平均化 | **棄却**（E1） |
| ② 更新量が小さすぎる | 未検証 |
| ③ 更新量が大きすぎて改善を壊す | **やや有力**（KL 0.096動いて勝率45.6→42.6%＝動くほど悪い） |
| ④ **Criticの特権情報が裏目**（Actorが使えない隠れ情報に強く依存） | **最有力** |

④の理屈: 特権ベースラインは**不偏だが分散削減の意味で最適とは限らない**。分散削減の
最適ベースラインは観測条件付き E[Q|o] であって状態条件付き V(s) ではない。Criticが
相手の手札を見ていると、同じ観測に対し隠れ情報次第でVが振れ、**Actorが条件付けられない
成分**（相手の事故手札で勝った/負けた）がadvantageに乗る。それで方策を更新すれば
無関係な方向に押され、③の「動くほど悪くなる」兆候とも整合する。

**自己訂正**: 私は当初これを「不偏だから安全」と判断して分散の観点を検討しなかった。

### 切り分け4: 特権情報がVに持ち込むノイズを直接測る（`tools`ではなく `selfplay/probe_privileged.py`）

**学習を回さずに機序を測る**手法を作った。相手の手札を「観測と矛盾しない別の手札」に
差し替えてVを再計算する。相手の未公開領域（手札 ∪ 山∪サイド）は我々からは区別が
つかないので、そこから同枚数を引き直した手札は**同じ観測に対応する別の隠れ状態**になる。

    σ_hidden = 同一観測内でのVの標準偏差（Actorが条件付けられない成分）
    σ_total  = 状態間でのVの標準偏差（Vが持つ情報の全体）

実測（40試合・3,017決定 × 8通りの隠れ状態、リーグ本走のCritic）:

| | 値 |
|---|---|
| σ_hidden | 0.1076（中央値 0.0917） |
| σ_total | 0.3647 |
| **比率** | **0.295** |

**Vの変動の約30%（標準偏差ベース）がActorの観測では説明できない成分**。同じ観測でも
相手の手札次第でVが±0.11動き、それがそのまま advantage のノイズになる。
事前に「0.3を超えれば逆効果の可能性が高い」と基準を置いており、実測はその境界上。

**確かなこと**: 特権情報はadvantageに無視できないノイズを持ち込んでいる。
**確かでないこと**: それが停滞の**主因**か（ノイズがあっても信号が上回れば学習は進む）。
→ E2（特権あり/なしの学習比較）で判定する。

**この手法自体が資産**: 「隠れ情報を再サンプリングしてベースラインの分散寄与を測る」は、
今後Criticに特権情報を入れるか判断するたびに使える。学習を回す前に効果の向き（というより
リスクの大きさ）が分かる。

### 切り分け5: 特権情報も更新量も主因ではない —— E2/E3

相手を101のみに固定し、方策はSL初期から、学習済みCriticを使い回して**3条件を完全同一条件**で
20イテレーション×1,000試合ずつ。学習前の 099 vs 101 = 45.6%(n=399)。

| 条件 | 訓練前半5回→後半5回 | 最終KL | argmax評価（5回平均） |
|---|---|---|---|
| A ベースライン | 43.4% → 44.7% | 0.087 | **41.5%** |
| **B 特権なし** | 44.0% → 44.9% | 0.090 | **41.6%** |
| **C lr 1/3** | 43.9% → 46.9% | 0.030 | **43.9%** |

**④（特権情報が裏目）は棄却**。特権を外しても 41.6% で、ベースライン 41.5% と実質同一。
σ_hidden/σ_total = 0.295 のノイズは実在するが**停滞の主因ではない**。
（私はこれを最有力と見ていた。外れた。）

**②（更新量が小さすぎる）も棄却**。lrを1/3にした方が良い＝小さいほど良い。

### 結論: 移動量と性能が単調な逆相関

| 最終KL | vs 101 argmax |
|---|---|
| 0（未学習） | **45.6%** |
| 0.030 | 43.9% |
| 0.087〜0.090 | 41.5〜41.6% |

**方策を動かすほど悪くなり、動かさなければ元のまま**。これは
「**勾配に行動固有の信号がほとんど無く、更新がほぼランダム歩行になっている**」
という説明と完全に整合する。よく調整された模倣方策から無作為に離れれば距離に比例して悪くなる。

**なぜ信号が出ないか（機序の見立て、3要因の重畳）**:

1. **探索が構造的に成立しない** — argmax一致率89.3%、実効選択肢1.29個（平均8個中）。
   9割の決定で「どうせ選んでいた手」を選ぶので、勾配はその確率を上下させるだけで
   **比較情報を含まない**。温度では直らない（T=2.0でも1.92個）
2. **信用割当の距離** — 報酬は終端±1のみ、1試合約80決定。連続する自分の決定の間に
   **相手の1ターン全体**とドローが挟まる。GAE(λ=0.95)の実効地平20決定でも、δには
   自分の手以外の寄与が大量に乗る
3. **飽和方策に対するクリップの非対称** — 選んだ手の確率が平均0.856。クリップ±20%では
   **上げる余地はほぼ無く、下げる余地は大きい**。しかも101に56%負けるので負の優位性が
   多数派になり、**模倣で得た自信のある手を削る方向**に偏る

**未検証で残した仮説**（実施すれば機序が確定する）:
- D1: 優位性の符号反転（A→−A）。同程度に劣化すれば「更新はノイズ」が確定
- D2: 勝ち越せる相手で訓練。改善すれば要因3（負けが削る）の寄与が確定
