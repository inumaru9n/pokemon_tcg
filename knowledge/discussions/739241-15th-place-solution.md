## 3行サマリ

- **7.5Mパラメータの recurrent actor-critic を、ランダム初期化から分散population自己対戦で学習**。
  BCも人間デモも**一切使わない**
- 提出物は **NN直接推論のみ**。実行時探索なし・エンジンrollout なし・カード固有の上書きルールなし
- **Slowking / Dragapult の2デッキのスペシャリスト**。合計 **5.5B decisions ≈ 5 GPU-days**（RTX4090×1 + 分散CPU actor）

## 1. モデルと入出力

| 項目 | 内容 |
|---|---|
| 規模 | **7.5M パラメータ**（我々の222系は約0.8M） |
| 型 | recurrent actor-critic（**再帰メモリで過去の決定を保持**） |
| 入力 | 現在のエンジン観測 + 利用可能な legal actions + 関連するカードの identity |
| 出力 | **legal action ごとのスコア**。評価・提出時は最高スコアを greedy に選択 |
| 追加構造 | 「行動を**周囲の盤面と他の選択肢との関係で**評価できる学習コンポーネント」＝
  盤面↔候補・候補↔候補の相互作用（24位のattention型・我々のpointer型と同じ問題設定） |
| critic | 最終結果の期待値を推定（**学習専用**。推論では使わない） |
| 補助目的 | 「**行動が引き起こす可視の変化**をネットに認識させる」補助損失を複数。
  ただし「どの戦略的選択が良いか」は定義しない（＝報酬シェイピングではない） |

★★ **複数選択（multi-part effects）は1決定ずつ扱う**: 選択するとエンジンが
「前回の選択が記録された次のプロンプト」を返し、また選ぶ。
これで**カード数・技・対象の個数が変わっても同一ネットで扱える**（我々の逐次選択と同じ設計）

## 2. 開発で効いたこと（本人の記述）

★★★ **初期エージェントの不可解な手の多くは「エンジン↔NNのインタフェース」の問題だった**。
リプレイでは自明な情報が、モデルに十分明確に表現されていなかった。
**観測とlegal actionの符号化を何度もバージョンを重ねて作り直した**のが効いた

★★★ **個別のミスをカード固有ルールで塞ぐことは意図的に避けた**。
直す対象は常に「ネットに渡る情報」と「自己対戦での学ばせ方」

## 3. 学習システム

- **多数のCPU actor が公式エンジンで対局し、GPU learner 1枚が更新**（actor-learner分離）
- actorとlearnerが連続稼働するため、**やや古い方策が生成した軌跡への補正**を入れている
  （＝IMPALA/V-trace型の off-policy 補正。本人は手法名を書いていない）
- **凍結した過去方策のpopulationを保持**。現方策は最近版と**選ばれた旧版の両方**と対戦。
  これで単純な忘却を防ぎ、「最新の相手だけを食い物にする」崩壊を起こりにくくした
- スペシャリスト学習では、**提出デッキ + 公開コンペデータから集めた広いデッキ群**を混ぜる。
  **両座席とも学習例に使い**、ミラーも他アーキタイプも経験させる
  （「1つの固定相手に最適化せず、提出デッキを深く学ぶ」のが目的）
- ★★★ **報酬は最終勝敗のみ**。ダメージもサイドも報酬にしない
  （「取れたこと自体が良い判断を意味しない」）

## 4. デッキ選択（Slowking / Dragapult）

**決定パターンが本質的に違う2つ**を選んだと明言:

- **Slowking** = 山の準備と「今の局面に適した技の選択」。最善手が相手盤面・残サイド・
  使えるエネ・後続に必要な資源で変わる → **状況依存の技選択を方策が学べるかの試験**
- **Dragapult** = ダメージの**配り方**と、それを将来のサイドに変換する判断。
  即時打点が最善を示さない（ダメカンの置き場所が後のKOを決める）→ **複数ターン計画の圧力**

2体は同一アーキテクチャで**逐次**学習し、**Slowking は Dragapult の系譜からwarm start**
（ランダム初期化からやり直さない）

## 5. 評価と推論時の判断

- ★★ **統制オフライン対局**: 候補と参照に**同一デッキを与え、座席を入れ替えたペア日程**で回す。
  方策の改善を「デッキ運・座席運」から分離する（＝我々のCRN/自動先後入替と同型）
- ★★★ **推論時の追加評価（探索）は試したが、直接の行動選択より悪かった**ので採用しなかった
  （736121 の「BC valueでは −20〜30点 / PPO valueでは +50〜70点」とは逆の結果。
  RL済み方策のvalueでも探索が勝てない場合がある＝**探索の可否は価値関数の質だけで決まらない**）
- ★★ **自己対戦中は方策分布からサンプリング**（探索のため）、**評価・提出時はgreedy**。
  理由: 残っている失敗は「予測可能性を相手に突かれている」のではなく**単なる戦術ミス**だから

## 7. 本人の総括

> 方策は「勝ちに結びつくパターン」を大量に学べるが、**ゲームの計算や戦略的依存関係を毎回正しく
> 再現できるわけではない**。勝率が上がったからといって、内部のメカニクスを正しく学んだとは限らない。

それでも「デモも実行時探索も、増え続ける手書きの戦術パッチも無しに、
大規模population自己対戦だけで有用なスペシャリスト方策が学習できた」ことが結果として示された。
